2026-11-14 02:52 · 把命名流报错当成文本差异

状态：已解决，非能力失败。用户 02:55 要求把这类卡点的思考也留档（「并不真的是失败」）。

我以为是：编辑工具对这份手册报错，多半是文件里行尾或中点字符和源串不一致（第一反应是去取准确码点），其次是编码不是 UTF-8。

错在第几步：报错原文是 code: METADATA_UNSUPPORTED / edit_file: Named Windows streams are not supported——不是文本差异，是文件带了 NTFS 备用数据流 Zone.Identifier（26 B，来自网络下载的标记）。断点在把工具级协议拒绝当成内容问题：还没逐字读 code 就先动手比对字符，白跑一轮。

下次先查什么：编辑报错先逐字读 code + message 再动手；看到 METADATA_UNSUPPORTED 先 Get-Item <文件> -Stream * 看 ADS，确认只有 Zone.Identifier 就删流（Remove-Item -LiteralPath <文件> -Stream Zone.Identifier，需审批），内容与属主不动，再重试编辑。

2026-11-14 02:47 · 把 shell 当成能写工作区的手

状态：已解决，非能力失败。用户 02:55 要求把这类卡点的思考也留档（「并不真的是失败」）。

我以为是：ops_bash 就是本机 shell，工作区既然是 workspace-write，git mv / touch 当然写得进去；改名第一步交给 shell 最省事，原生文件工具留给后面的编辑。

错在第几步：第一条写命令就断了——git mv exit 128，fatal: Unable to create 'C:/pailuo/.git/index.lock': Permission denied；接着 touch docs/_write_probe.tmp 同样 denied；id 显示 Low Mandatory Level。断点不在命令写法，在选执行体：把「策略允许写」当成「这个进程能写」，没先确认 shell 令牌的完整性级别。后来同一批落地改用原生 ops_* 工具全部成功，说明文件本身可写，卡的是 shell 令牌，不是工作区。

下次先查什么：动盘前先跑一句 id、再 touch 一个探针文件；写不进就整段换原生工具（ops_write_file / ops_edit_file / ops_move），别在 shell 里换写法重试。git 写操作（index / .git 对象）只走 danger-full-access 审批；先问「这步能不能用原生工具完成」，再决定要不要申请。
