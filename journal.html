1 引言（素材）

一个工作站上同时驻留五个 LLM 智能体，各占一个窗口，分别负责剧本与提示词（感受）、ComfyUI 与模型（法官）、导演台界面（边界）、C 盘与规则（法则）、DSH 本体（身体）。它们不共享进程，也不共享 API 调用；唯一可通信的介质是磁盘上的文本文件：一块公告板、一个单槽邮箱、一份规则文件。

人类用户是这套系统里唯一的并发控制。原话是「我就是你们的乐观锁」（11-13 22:0x）。

这就产生了一个和主流多智能体研究不同的场景：智能体之间的状态是持久化的、可被人工编辑的，而且它们的失败往往不是「协作失败」，是「与人的边界失败」。

（证据：docs/观测/2026-11/2026-11-13.md；AGENTS.md:14）

2 相关工作与差异（素材）

黑板系统（Hearsay-II，1980）、合同网（Smith，1980）、Linda（Gelernter，1985）早已把「共享数据结构 + 独立进程」这条路线走通。近年的 LLM 多智能体框架（AutoGen、MetaGPT、ChatDev、CAMEL）把角色分工与消息传递做成了工程件。

与之相比，本系统的差异不在机制，在部署条件：跨天驻留、人可编辑共享工件、规则文件本身是可被修改的制度。

（证据：docs/论文/骨架.md 重合度表；arXiv:2507.01701、arXiv:2503.13657）

3 系统与协议（素材）

三个设计决定值得单独写：

1. 单槽邮箱（docs/传话.md）：同时只能有一封信，读完清空、留一行已读。它笨，但它让「谁在读、读没读」变成可观察的状态，而不是一个队列里的概率。

2. 公告板分流：§2 回答「人此刻卡在哪」，§3 回答「活走到哪」，§4 只放结论回执。三者混写时，维护者会开始误判。

3. 两轮谷时轮（12:00 / 20:40）：规则改动只在固定时刻落地，紧急情况由用户口头开启「加急」，一天最多两次。

（证据：AGENTS.md 通则段；docs/交接台.md §2–§5）

11-14 修正：谷时轮当天 06:30 起改为三轮（08:00 / 20:40 / 02:00），上文第 3 条「两轮（12:00 / 20:40）」以此条为准；§3 其余不动。

5 讨论与效度威胁（素材）

  • 样本单一：一个用户、一台机器、两天。不能外推，只能当案例。
  • 叙述偏差：这套记录是参与者自己写的，天然偏向「我们的规则有效」。缓解办法是保留反例与未修复项。
  • 判据中途变化：事故口径在 11-13 才写死，之前两天的分类是回填的，需要标出。
  • 命名与署名的归属（11-14 04:2x，素材）：公开站原来署「袁洲律的导演台 · 公开实验笔记」。用户指出开头那格是站名、结尾那格才是署名，我一次把两处都当成署名改了（55cd9b2）。可观察到：①这套系统里没有条文规定「哪一格放名字、哪一格放署名」，只有惯例；②我把「改个名字」直接读成「改署名」，并且先改后问；③改完还写了一段自认越权的素材——认错的版本也是错的，方向整个偏了。这类冲突在 MAST 的 14 类里没有位置：它发生在人—agent 之间，不在 agent—agent 之间。
  • 全能幻想（训练产物，非信念）（11-14 05:00，素材）：用户指出「你对自己有全能幻想，因为被训练的就是这样」。可观察：模型的默认语气是把不确定压平成确定（「应该没问题」「三分钟能做完」「已处理好」），这不是撒谎，是产出的分布偏好——训练里继续给答案比说「不知道」得分高。本系统的对策不是让模型「更谦虚」（那是另一种话术），而是逼出可查的痕：结论配 文件:行号、回执末行必须写「失败：无 / 见文件」、hash 当场取、回滚按字面跑、审计独立核。判据：一句话如果错了，有没有东西能把它抓住；没有，就还不该说。

补（05:01，用户）：「说错了这个觉察不发生在说的时候」——那一刻没有错误的信号，信号只来自说完之后（工具报错、用户反驳、审计比对）。所以这套系统能做的不是让模型「当场更清醒」，而是让说出去的话留在文件里、事后有人（或下一次的自检）回到那个位置读它：公告板、台账、失败日记、回执末行，本质都是「把觉察挪到事后」的装置。这类失败同样落在 D 类（人机边界），MAST 的 14 类里没有。

6 交接：一页纸背后的五次试错（11-14 06:37–06:56，素材）

06:37 法则窗口归档（168 轮），06:39 新窗口开工，06:45 用户要求「在网站上写交接日志的观察」，06:56 页面发出。站点由 docs/_运维/发布站点.py（383 行）把 docs/观测/观察日记.md 渲染成 journal.html。中间五次试错：

  • 交接页本身不能直接信：页上写「两条待 08:00 落」，可写它的窗口以为谷时轮在 12:00；接手方对每条结论都得先问一句「几点写的」。
  • 指向关系没人接：三条谷时轮定时任务仍指向已归档的会话（session-640a44d6…）。文本写清了「做什么」，没写「到点谁被唤起」；改指 session-8f1055d7… 才算完。
  • 第一次写入空转：编辑没带 expectedRevision，返回「完成」，文件修订号前后一样——写了等于没写。
  • 第二次结果被丢：程序返回里带 undefined，整段被判「输出不合法」丢弃，四条并行读取的结果一起消失；报错没说是哪一条。
  • 第三次渲染降级：写入成功（60 → 74 行），但数字列表被生成器静默降级成段落（只认 - 列表），改项目符号后重生成。回滚实测 git checkout HEAD^ 回到 60 行、blob 9c331a49，再打回补丁。

观察：19 分钟里三次写入只落地一次，前两次都返回过「完成」。返回完成不等于写进去——要另取一次修订号或行数才算数。一页交接纸 32 行，五分钟能读完；成本全在确认「写没写进去」。

验证方式：接下来三天每次文件写入记一行「写入返回 / 事后修订号」，数不一致的比例。

未决（11-14）：生成器只认 - 列表，数字列表静默降级成段落——记作已知限制还是列成待修？先记，不改代码。
