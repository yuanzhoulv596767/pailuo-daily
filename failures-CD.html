F-13 · 把「观察」写成结论汇编（11-14 06:49）

我以为是：观察日记是论文素材，写的是「问题与假设」，不该写过程流水账。所以我给公开站点写交接观察时，压成三条结论——状态能转移但有效期不能、最容易漏的是指向关系、状态重建靠读盘。读起来干净，也符合日记头注「不写解决方案、写判断」。

错在第几步：写作那一步。我把「只写判断」当成了「只能写判断、不必写事实过程」，但日记头注要的是「此刻看到的问题、我的假设、打算怎么验证」——问题首先得让人看见。三条结论里没有一条能让读者看到这 19 分钟里发生了什么、失败了几次、成本在哪；也没有一条落到具体文件或提交号，只有抽象说法。用户 06:49 一句「是不是没写清楚？这么长时间的试错？」直接指出：干净不等于清楚。对比证据：§6 初版（a92c8ca）与改写版（c405b41）写的是同一件事，后者多了时间线、五次失败、三次写入只落地一次的数字。

下次先查什么：给公开页面写「观察」前，先列三样再动笔——①时间线（几点到几点）；②这段时间的失败次数与每次的失败类型；③每条判断对应的 文件:行号 或提交号。三样齐了再决定抽象到哪一层；缺一样，写出来就是结论汇编。判据只有一条：读者能不能沿着锚点把这 19 分钟重走一遍。

F-12 · 用五分钟前的读数报「槽是空的」（11-14 06:26）

我以为是：06:19 我读过一次槽，里面没有消息块；06:24 用户问「？」时，我把那个结论直接说出去——「槽是空的，已读记录在」。

错在第几步：06:24 那句判断。docs/传话.md 的 mtime 是 06:21，身体那封信是 06:21 写进去的；我在 06:19 读的是写之前的版本。差两分钟，我把「上一刻空」当成了「此刻空」。

下次先查什么：报槽/板/任何"现在是什么状态"之前，当场重读一次，并报出 mtime 或字节数（wc -c + ls -la）。读数带时间戳；没有时间戳的读数只能说明过去。

F-11 · 格式串少了一个参数（11-14 06:06）

我以为是：%s%d 条%s 这段，前面加了个「按需开 · 」前缀，把 %s 从两个改成三个，参数表照着补就行——反正 Python 会告诉我缺哪个。

错在第几步：改完没跑就往下走了吗？没有，跑了，报的是 TypeError: %d format: a real number is required, not str。真正错在参数表里多塞了一个 names[k]：模板是三个 %s 一个 %d，我给了四个 %s 一个 %d，于是 %d 收到了字符串。报错指向的是「类型不对」，不是「数量不对」，我第一眼还以为是数字算错了。

下次先查什么：改 % 格式串，先把模板里的占位符数一遍（%s/%d 各几个），再数参数个数，两个数对上才跑；报 TypeError: %d format 先怀疑位数错位，不是取值错。

F-10 · 覆盖了槽里一封未读的信（11-14 05:59）

我以为是：槽里那封「法则→身体 05:50」我已经看过了（我读的是自己写的），所以重写槽时按「保留已读行 + 新消息」拼，从第一个 --- 往后全替换就行。

错在第几步：写文件那一步。前一条命令我读过 head -12 docs/传话.md，屏幕上就有那封 05:50 的信；写的时候我用 split('\n---\n') 取 head，直接丢掉后半段——等于把一封还没人读的信删了。而且我当时的判断是「这封是我发的，我再发一封新的就行」，漏了它里面有一整份评估委托。

下次先查什么：动传话槽前，先 git show HEAD:docs/传话.md 把收话方和状态看清楚——「我自己发的」不等于「对方读过了」。重写槽的办法只能是「在消息块后面追加」，不整段替换；要替换先 git log -- docs/传话.md 看上一封是否有 已读 记录。

F-09 · 时间先写后发生（11-14 04:15）

我以为是

头里写「04:05」、日志里写「04:06」，只是近似；反正几分钟后就提交了，读的人不会在意。

错在第几步

第一步。时间戳是这系统里少数可对账的字段——审计拿它比 git log，一比就出「记录晚于提交」。我写的是我以为会到的时间，不是已经发生的时间。

下次先查什么

写时间前先取一次当前时间（date +%H:%M）；或先提交、再按提交时间回填。宁可写「约 04:0x」，也不写一个还没到的钟点。

F-08 · 回滚命令没按字面跑过（11-14 04:14）

我以为是

回滚命令只要写清「改前 HEAD + 文件名」就算数；我确实做了往返实测，所以「实测过」已经满足规则。

错在第几步

第二步。「实测了 hash 一致」不等于「实测了那行命令」——我核的是 git checkout <hash> -- AGENTS.md 单文件形式，写进回执的却是两个文件那行，第二个路径少了 docs/交接/，按字面跑必报 pathspec 错。命令是给别人抄的，抄的人不会替我补路径。

下次先查什么

贴进回执之前，把那行原样粘进 shell 跑一次；跑通后再 checkout 回 HEAD 确认干净。核 hash 是核结果，跑命令才是核交付物。

F-07 · 把 git blob 当成 sha256（11-14 04:13）

我以为是

git hash-object 出来的是「这个文件的 hash」，回执里写「改前 sha256」没问题——反正都是 hash，能对上就行。

错在第几步

第一步就错，错在没定义「要哪种 hash」。git 的 blob 是 SHA-1 (40 位)，sha256 是 64 位；我把前者写在了后者的名字下面。读回执的人按 sha256sum 复算，永远对不上，还会以为文件被改过。

下次先查什么

写 hash 之前先问「这个值将来给谁验、用什么命令验」。完整性锚点用 sha256sum（64 位十六进制）；git 内定位用 git rev-parse <commit>:<path>（blob）。两者都能用，但表头必须写明是哪个，并且与生成它的命令一一对应。

2026-11-14 03:57 · 明细里的改前 hash 又是猜的

我以为是：AGENTS.md 的改前 hash 我记过（7581e17f），docs/失败日记/README.md 顺手写一个 ca2d9de4 就行——反正一会儿回滚实测会核。

错在第几步：写明细那一步。hash 是我凭印象填的，实测只核了 AGENTS 与 README 的「改后」，改前那一格没回头比。核出来真实值 9085aa34，差的不是一位，是整个值。

下次先查什么：明细里的每个 hash 都必须用 git show HEAD~1:<文件> | git hash-object --stdin 当场取，取完再写；「等会儿实测会核」不算核，实测如果是照着错的基准做的，就一起错。

2026-11-14 02:47 · 把「实测」写在跑之前

我以为是：改名往返是纯 git mv，跳转壳是另一个文件，不会挡路；先把明细里的「实测 ✅」写完，再照单跑一遍就行。

错在第几步：写的时候就错了。明细的实测段先落了「git mv docs/CD-brief.md docs/C盘管理-brief.md → hash 不变 ✅」，然后才去跑——第一步直接 fatal: destination exists, source=docs/CD-brief.md, destination=docs/C盘管理-brief.md，因为跳转壳正占着旧名。不是命令写错，是顺序反了：结论先于执行。

下次先查什么：① 明细里凡是「实测」两个字，落笔前必须已经跑完并看到输出；② 改名类回滚先 ls 目标名是否被占（壳、旧文件、大小写别名），占了先删再 mv；③ 回滚命令里出现 git mv，就默认它可能撞名，别当无风险操作写。

F-04 · 「报错之后照跑」第二次，因为我只改了规矩没改写法（11-14 01:56）

  • 我当时在解什么：把失败日记改成一人一文件夹，同时要改 docs/_运维/发布站点.py 让站点按文件夹合成。习惯上我一次调用里跑完：改脚本 → 跑脚本 → 核验 → commit。
  • 我怎么推的：①这几步是一条链，顺序固定 → ②写在同一个 bash 块里最省事 → ③F-01 的教训是"要用 && 串"→ ④我在 python 脚本.py 和后面那条之间放了 &&，觉得已经守规矩了。
  • 哪一步开始错：第③步。&& 只串了「改脚本」和「跑脚本」之间那一段，后面 python -c 核验 与 git add && commit 是另起行写的，等于又回到了换行分隔。所以脚本抛 TypeError（我替换函数时漏了旧的 print），核验被跳过，commit 照样执行——把没跑通的状态提交了。同一次调用里我还写了个 PYEOF 后换行接 && 的块，bash 直接语法错，前后两件事都是同一个毛病。
  • 为什么会走到那一步：我把 F-01 的教训记成了「记得用 &&」，于是只在脑子里觉得相邻的两段之间加，没意识到真正的规则是「一个事务只能有一条命令链」。规矩记成了一个动作（加符号），而不是一个结构（整块唯一入口）。
  • 正确的推法：链一旦超过三步，就不要在 bash 里拼——写成 .sh 或 .py 文件一次跑完，里面的失败自然中断；或者拆成多次调用，每步看结果再走。
  • 下次的检查点：一条命令里出现两个以上 python/git/mv 时，先落成脚本文件再跑，不许在对话里拼多行链。

F-02 · 回滚路径混用「改前/改后」，把两步并成一步（11-14 01:19）

  • 我当时在解什么：git mv 之后要做回滚往返实测。我以为回滚就是一条 git checkout HEAD -- <文件>。
  • 我怎么推的：①回滚＝回到 HEAD 的样子 → ②HEAD 里有什么我就 checkout 什么 → ③文件列表照抄刚才改过的那批，最省事。
  • 哪一步开始错：第②步被我一笔带过，第③步就摊上了。HEAD 是改后的世界，而 docs/论文/草稿.md 因为 git mv 已经从 HEAD 里消失了。
  • 为什么会走到那一步：我把"回滚"理解成一个时点操作，其实它是路径操作——同一个逻辑文件在改前/改后有两个不同路径，必须分别处理，不能拿一个文件列表套两次。
  • 正确的推法：先问"这个文件在改前叫什么、改后叫什么"，再分两条命令写：退到旧路径 + 删新路径，回则只碰 HEAD 现存路径。
  • 下次的检查点：涉及 rename/mv 的改动，回滚命令必须先写路径映射表，再写命令。

F-01 · 我把「文件肯定是 LF」当成了推理前提（11-14 01:15）

  • 我当时在解什么：改 docs/论文/README.md 上一段文字。我以为的关键约束是——这文件是 python 自己写出来的，换行必然是 \n，只要把目标串按 \n 拼好，assert 一挡就万无一失。
  • 我怎么推的：①文件是本窗口写的 → ②写的时候用 \n → ③所以文件里就是 \n → ④按 \n 匹配安全 → ⑤加 assert 更安全。
  • 哪一步开始错：第②步。「我写的时候用什么」不等于「磁盘上留下什么」——中间还有 git 工作区、.gitattributes、编辑器保存策略。
  • 为什么会走到那一步：我把"我发出的字节"当成了"文件里的字节"。这是用自己的输出反推系统状态，而这台机器上已经有过先例：_scrap 那次我也是先动了才问归属。「谁最后写的」不等于「现在是什么」。
  • 正确的推法：动手前先 file/od 看一眼真实换行，或者干脆用 read_text().replace("\r\n","\n") 归一化——把不确定性消掉，而不是赌它不存在。
  • 下次的检查点：凡是我自己写过的文件，都当作"别人写的"重新看一眼再改。
