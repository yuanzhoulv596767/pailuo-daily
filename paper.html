定位

经验型系统报告（experience / system report），不是框架论文。

不声称提出新协议——黑板 + git 已有前人做过，硬撑会被一句「这不就是 blackboard + git」打死。

一句话：在只有文件系统可通信、上下文会互相污染、人必须保留否决权的条件下，五个长期驻留的智能体窗口如何协作，踩了哪些坑，补了哪些条文。

三条贡献（降级版）

1. 一种部署形态的观察：真实工作站、跨天驻留、五角色、纯文本工件 + git 对账

2. 一份事故 → 条文的转化清单，补 MAST 缺的一块：人—agent 边界类失败

3. 一组可复位的设计原则：单槽邮箱、结论/明细分家、用户即锁、报错落点三分

五节

1. 引言（场景与三个结构性差异，1 页）

2. 相关工作与差异（黑板 / 框架 / MAST，1 页）

3. 系统与协议（工件 + 五条设计决定，2 页）

4. 运行观察与事故清单（2 页，主体，先写这节）

5. 讨论 + 效度威胁（1 页）

先不写：实验、对照、benchmark、形式化证明。

唯一独家点

人—agent 边界失败：越权做别人的活、先删后立规的时序错位、mtime 审计误报、用旧记忆报状态。

MAST 的 14 类里没有——它研究同一进程内的智能体；人也在共享工件里读写时，才会出现「人与 agent 争同一状态」。
