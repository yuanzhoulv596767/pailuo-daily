2026-11-14 06:57 · 拿 list_sessions 的 live 当「窗口还开着」的判据

我以为是

list_sessions 里 live: true = 这个会话正在被使用；两个都叫「派萝-法则」且都 live:true，就是两个窗口同时在跑，会互相打架 → 于是向用户提「要不要我把旧的改名归档」。

错在第几步

第 1 步判据就错了：live 只说明会话被加载过、没被彻底释放，归档后的会话仍可能 live:true，而归档动作本身会写盘（旧会话 06:55 写入），我把「文件在动」当成了「窗口在用」。用户贴出侧边栏截图（只有一个法则、5 分钟前）才推翻这个判断。

下次先查什么

1. 判「窗口是否并存」先看用户界面或 docs/交接台.md §2 五行，别只看 API 的布尔位。

2. 要下「会有两窗打架」的结论前，至少两个独立证据：存盘 mtime 和 标题/编号，且指明哪个是新窗口。

3. 拿不准就先问一句，别先给方案——方案本身会把用户带进错误前提。

2026-11-14 06:20 · 传话槽追加段没写进去，却向用户说「已投槽」

我以为是

str.replace(旧句, 新句) 只要 python 退出码是 0，文件就改了；而且我改完立刻用 grep 查了「24 行 / 15 条」在不在——在的（那是 06:18 就写进去的旧内容），于是判定「追加成功」。

错在第几步

第 2 步（写入）静默失败：replace 的匹配串结尾我假设了换行，实际文件末尾没有那个换行，replace 一个字符都没替，write 又把原样内容写回磁盘。第 3 步（验证）我验的是「文件里有没有 06:18 那条」，不是「有没有 06:20 新增的那段」——验了个已经成立的条件，等于没验。

直接后果：06:21 用户报「传话槽她说空的」，我第一反应是往「她路径不对 / 缓存」上找，实际是我这边根本没写进去。

下次先查什么

1. 任何改文件的脚本，写完读回新内容的那一行（in 判断新句子 + print(len(bytes)) 变化），三秒的事。

2. replace 前先 assert 旧句 in 文本，不成立就抛错退出——静默的 none-op 比报错危险。

3. 向别人报「已投槽 / 已落地」前，那条报出去的判据必须是本次新增的东西，不能是上一次就存在的东西。

F-03 · 日志写 FAIL，其实远端早就成功（11-14 00:26）

我以为是

脚本只在 git push 退出码非 0 时写 FAIL，写了 FAIL 就是没推上去；本机 github.com:443 又确实不通，顺着网络查最省事。

错在第几步

把「退出码」当成「操作结果」。git push 是两步：更新远端、再更新本地跟踪引用；.git/refs/remotes/origin/main.lock 残留让后一步失败，于是内容上去了、日志写着失败。同一处还漏了反向：robocopy 8+ 是真失败，却没人判。

下次先查什么

判结论看状态不看退出码——git log origin/main..HEAD 加远端内容两处对一遍。

F-01 · 搬目录没先查 ACL（11-13 22:04）

我以为是

同盘搬目录只是改个名，秒级、可回滚；先停掉进程就算稳了。目录所有者是我自己，不会有什么拒绝项拦路。

错在第几步

第 1 步就错了——把「能读能写」当成「能改名」。同盘改名实际是「复制 + 删除」，目录里那条 Everyone:(CI)(DENY)(DC) 正好拒绝删除子项，于是复制完删不掉，留下 724 文件在 C 盘根、838M 在原地，两边都不是完整仓库。

下次先查什么

动手前 icacls <目录> /show 看有没有 DENY，再拿一个废弃子目录做一次 Move-Item 往返。

F-02 · 在错误宿主上排查四十分钟（11-13 21:50）

我以为是

工具的消失等于插件加载失败；3080 那个 dsh web 就是我所在的宿主——日志、profile、端口全都对得上。

错在第几步

第 0 步没做：确认「我是谁的子进程、它读哪个 profile」。我先接受了最顺手的假设，之后每一步都在一个早已停摆的进程链上取证，证据全是真的，只是属于别人。

下次先查什么

Get-CimInstance Win32_Process 看自己的父进程命令行，宿主不明不动配置。
